# 内部使用与交付说明

## 启动和登录

在 `crawler_system` 目录执行：

```powershell
npm start
```

启动完成后访问 `http://127.0.0.1:8093/`。后端健康检查地址是 `http://127.0.0.1:8000/health`。管理员可以维护账号、来源、关键词并手动重跑任务；普通用户可以查看、筛选并保存“我的关注”。个人关注按账号隔离，管理员设置的全局重点与跟进状态不受影响。交付文档不记录密码，密码由管理员单独告知。

## 看板字段

- 高优先级：命中了高优先级关键词或明确的项目申报业务信号，表示需要优先关注。
- 关键词命中：公告标题或正文命中了当前启用的关键词规则。
- 采集完整度：根据标题、正文长度、乱码和结构完整性计算，范围为 0–100；只反映采集结果是否完整，不代表公告价值、相关性或重要性。
- 发布日期：网站提供的业务发布日期。网站没有日期时，公告中心会明确改用采集日期。

## 采集异常怎么处理

首页出现“采集运行异常”或“采集数据已过期”时，提示框会直接列出异常来源、运行状态和最近原因。

- 管理员：点击异常来源右侧的“重新运行”，然后到“系统管理 → 任务/日志”查看结果。
- 普通用户：把提示中的来源和原因反馈给管理员，不需要自行操作任务。
- 部分完成：成功内容已经保存，但本次还有个别列表页、详情页或主题失败。
- 已过期：该来源超过 24 小时没有成功更新，当前数据可能不是最新。

常见原因包括目标网站超时、HTTP 403/429、验证码、网络无法连接，以及网站改版导致页面结构未匹配。系统不会绕过登录、验证码、付费墙或平台风控。

## 刷新频率

每个来源按“系统管理”中显示的 cron 表达式定时执行。当前政府项目来源通常每天 08:00 和 14:00 分批运行；会议来源通常每天 09:00 和 15:00 分批运行；PubMed 与 ClinicalTrials.gov 通常每天 10:00 左右运行。实际时间以任务配置为准，页面上的“刷新看板”只重新读取数据库，不会主动重新爬取。

## 交付前一键检查和备份

确保 `npm start` 正在运行，然后执行：

```powershell
npm run delivery:check
```

该命令会：

1. 逐一核对 12 个应启用的自动采集来源；
2. 检查最近运行是否成功、是否在 24 小时内更新；
3. 检查前端 `8093` 和后端 `8000` 是否可访问；
4. 使用 SQLite 在线备份 API 创建一致性数据库备份并执行完整性检查；
5. 把详细结果写入 `artifacts/delivery-check-latest.json`。

需求1按“信息类型覆盖”验收，不按“每站至少两条”验收。报告中的实际数量来自数据库；如果最近滚动列表暂时没有某一类公告，但同一官方网站的历史公告已经用同一解析规则通过回归验证，检查会显示 `WARN` 并附官方证据，不会伪造一条“今日数据”。如果既没有实际数据，也没有受验证的官方能力证据，仍会显示 `FAIL`。

备份默认保存到 `backups/data.YYYYMMDD-HHMMSS.db`，该目录不会提交到 Git。只有命令最后显示“可以交付”时，才应签署内部交付。

如需恢复备份，先执行 `npm stop`，保留现有 `server/data.db`，再把选定备份复制为 `server/data.db`，最后重新执行 `npm start` 和 `npm run delivery:check`。不要在服务运行时直接覆盖数据库。

正式放入公司内网时，不使用本地开发启动器；按 [内网部署、升级与回滚](intranet-deployment.md) 使用生产 Compose，让 Nginx 同源托管前端并代理 API，只对内网开放一个端口。

生成可直接转交内网运维的离线包：

```powershell
npm run release:intranet
```

发布包位于 `artifacts/intranet-package/`，同时生成整个 ZIP 的 `.sha256` 校验文件。包内 `verify.ps1` 校验逐文件清单，`deploy.ps1` 首次初始化配置和数据，`upgrade.ps1` 会先备份并保留活动配置与 `runtime` 数据。

服务每次启动会先创建经过 SQLite 完整性检查的数据库备份；运行期间每天上海时间 03:30 再执行一次备份与清理。默认保留 14 天备份与快照清单、30 天导出文件、90 天运行日志，`.gitkeep` 占位文件不会被清理。

## 外部来源边界

- 摩熵医药需要合法授权，不会绕过登录或付费限制。
- 外部网站可能临时改版、限流或触发验证码；最终交付机还应分别运行 `check_requirement1_sources.py`、`check_requirement2_meetings.py` 和 `check_requirement3_pubmed.py`，留存需求 1–3 原始 JSON 证据。
